# Rules — Conventions and Conformance

These rules check the project's own documented conventions. They
fire only when the discovery pass found a guide; without one, this
category is a no-op (best-practices fall to the other rule
catalogs).

The shape of each finding here is convention-specific — the rule
is "does the diff conform to what the guide says?" The audit
extracts auditable invariants from the guide (see
`references/discovery.md` §3) and checks each against the relevant
files. Severity is almost always **Nit** unless the convention
also covers a real risk surface (then it escalates per the other
catalogs).

---

## V1. `page.tsx` must be a thin server layer

**Question (when the guide says so):** Is every `page.tsx` under
the documented line limit, free of `"use client"`, and renders
exactly one component from the page-components folder?

**Apply to:** every changed `src/app/**/page.tsx` (diff mode) or
all of them (full mode).

**Prove it by:** read the file. Count lines (per the guide's
limit). Look for `"use client"` at the top. Count JSX literals in
the default export's return — more than one component (excluding
trivial wrappers like `<Suspense>` if the guide allows them)
violates the rule.

**Good finding:** "`app/multas/page.tsx` is 78 lines (guide §3
caps `page.tsx` at 30). The file inlines hero JSX, an FAQ array,
and the section composition that should live in
`components/pages/Multas/`. Extract to a `MultasPage` component
and have `page.tsx` render it."

**Don't report:** thin client-page wrappers when the guide
explicitly permits them (e.g. checkout pattern). Off-by-one near
the limit (don't quibble at 32 if the limit is 30 — the spirit is
what matters).

## V2. Server action auth pattern conformance

**Question (when the guide documents an auth pattern):** Does the
action follow the documented pattern verbatim, or does it use an
ad-hoc auth check?

**Apply to:** every `"use server"` export.

**Prove it by:** compare against the guide. If the guide says
"every authenticated action starts with `await auth()` then looks
up the user", and the action uses a different helper, flag the
divergence. The check still passes — this is a convention finding,
not an auth bug.

**Good finding:** "`app/actions/coupons.ts:18` reads
`headers().get('cookie')` and decodes the session manually instead
of calling `await auth()` per guide §5. Both produce the same
session, but the divergence makes future auth changes risky.
Replace with the standard pattern."

**Don't report:** action helpers that *wrap* the standard pattern
(call `auth()` themselves) — the convention is preserved.

## V3. ID generation convention

**Question (when the guide names an ID generator):** Are new IDs
generated with the documented helper?

**Apply to:** lines that introduce new IDs (`insert({ id: ... })`).

**Prove it by:** check the import. If the guide says `nanoid`,
flag `crypto.randomUUID()`, `uuid()`, `Math.random().toString(36)`,
manual concat patterns. Different ID schemes don't break anything
— they fragment the codebase.

**Good finding:** "`app/actions/dms-plans.ts:24` does
`crypto.randomUUID()` for the new plan ID; guide §8 says
`nanoid`. Existing plans use nanoid, mixing schemes makes admin
lookups awkward."

**Don't report:** IDs generated by the database (autoincrement,
default), foreign keys.

---

## V4. Class-merging convention

**Question (when the guide names `cn()` or similar):** Are class
strings merged via the documented helper, or via direct
`clsx`/`twMerge` imports?

**Apply to:** components using class composition.

**Prove it by:** grep for direct `clsx(...)` or `twMerge(...)`
calls in components when the project exports a `cn()` wrapper.

**Good finding:** "`components/dms/LeadCard.tsx:8` imports `clsx`
and `twMerge` directly; guide §12 says use `cn()` from
`@/lib/utils`."

---

## V5. Migration → schema doc sync

**Question (when the guide requires a schema doc):** Did this PR
add a migration without updating the documented schema?

**Apply to:** diffs that touch `src/migrations/` (or the
documented migrations folder).

**Prove it by:** in diff mode, check whether the schema doc
(`dbschema.md` per this guide, or as named in the project) is
also in the changed files. Full mode: cross-check the latest
migrations against the schema doc's last-modified time and
content.

**Good finding:** "`migrations/20260612120000_add_partner_table.js`
is in the diff, but `dbschema.md` is not. Guide §19 requires the
schema doc to be updated for every migration."

**Don't report:** non-schema migrations (data backfills with no
shape change) — but flag them anyway if the guide doesn't
distinguish.

---

## V6. Component placement

**Question (when the guide documents a component folder
structure):** Are new components placed in the right folder per
the guide?

**Apply to:** new components added in the diff.

**Prove it by:** read the guide's component taxonomy
(`ui/`, `pages/`, `layout/`, etc.) and check the new file's path
against the role implied by the file.

**Good finding:** "`components/MyFeatureButton.tsx` is at the
top of `components/` but is a UI primitive (just renders
`<button>` with variants). Per guide §10, primitives live in
`components/ui/`."

**Don't report:** edge cases the guide doesn't explicitly cover.

---

## V7. Path alias usage

**Question (when the guide mandates `@/` aliases):** Are imports
written with the alias or with relative paths?

**Apply to:** changed files' import statements.

**Prove it by:** grep for `from '\\.\\.\/` (`../`) imports beyond
a configured depth. Some teams allow `./` for same-folder; others
require `@/` everywhere.

**Good finding:** "`components/pages/Checkout/Checkout.tsx:4`
imports `'../../../lib/db'`. Guide §20 mandates `@/` prefix:
`'@/lib/db'`."

**Don't report:** same-folder relative imports (`./`) unless the
guide bans them too.

---

## V8. Metadata builder usage

**Question (when the guide names a metadata builder):** Does every
page export metadata via the documented builder?

**Apply to:** changed `page.tsx` files.

**Prove it by:** look for `export const metadata` or
`generateMetadata`. Compare against the guide's builder
(`buildPageMetadata`, etc.) — pages using raw `Metadata` objects
miss canonical / OG / Twitter defaults.

**Good finding:** "`app/legal/terms/page.tsx:1` exports
`metadata = { title: 'Terms' }` directly. Per guide §13, use
`buildPageMetadata({...})` so canonical URL and OG tags are
generated."

---

## V9. Service layer usage

**Question (when the guide mandates a services layer):** Does
this server action call the DB directly when a service helper
exists?

**Apply to:** actions doing `db('users')...` when there's a
`services/user.ts`.

**Prove it by:** check whether a service module exists for the
table being queried. If yes, the action should call the service.
If no, this is a Nit at most — maybe even no finding.

**Good finding:** "`app/actions/admin.ts:42` does
`db('users').where({ id }).update({ banned: true })` inline; per
guide §9, user mutations go through `services/user.ts` so audit
logging and validation stay consistent."

---

## Cross-cutting

- All convention findings are **Nits by default**. Escalate only
  when the convention also covers a real risk (e.g. V2 violation
  that happens to skip the auth check — that's an A1, not a V2).
- Quote the guide section in every convention finding. Without the
  citation, the finding looks like the audit's taste — exactly the
  failure mode this category exists to avoid.
- One convention violated in many files = one finding, with the
  locations listed. Don't repeat the rule explanation per
  location.
- If the guide rule itself is wrong/stale (e.g. references a
  helper that no longer exists), don't enforce it — note it in
  the "checked clean" section as "guide rule X appears stale".
